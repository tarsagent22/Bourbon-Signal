# Shopify cohort runtime integration contract

This is preparation only. Neither the candidate manifest nor the new descriptor helper is imported by a runtime registry. The five candidates are not activated, admitted, scheduled, or counted as fulfilled new stores. The existing CA Mission Trails / FL Jensen pilot remains unchanged. No production access or source request was needed for this integration review.

## Prepared components

`engine/src/collectors/shopify-cohort-runtime.mjs` provides `buildShopifyCohortDescriptors(configurations, { admissions, collectorSha256, catalogSha256 })` and `shopifyCohortScopeMatches(descriptor, row)`. Both are pure: no files, environment, network, database, scheduling, collection, or sends. The default admission list is empty, so passing the research manifest alone returns no descriptors. All returned descriptors are deeply frozen and `disabled: true`; there is deliberately no enable argument.

An explicit admission must bind one known runtime source ID to the validated configuration hash, reviewed collector code hash, and exact expected Bottle Bible byte hash. Building any descriptor requires the caller's `catalogSha256`, and each admission's `catalogSha256` must equal it; the bound hash is retained on the disabled descriptor. The current reviewed local catalog is `e5883ec9034802bff14dcae918fba4abc7d9baf2f5cc069c6013469e027e82be`. Missing or mismatched catalog bindings fail even when a canonical review artifact hash is present. The admission also supplies reviewer/time, production commit, policy snapshot, hashes of the reviewed admission artifact, canonical review, frozen premises baseline, and allowed live preflight. Every configured store/product/variant tuple needs a canonical ID and eligible tier. Unknown sources, duplicates, partial tuples, mismatched hashes, ineligible tiers, and unresolved baseline outcomes fail closed. Accepted baseline categories distinguish confirmed net-new inventory connections, recovery, and directory reuse; they do not equate these outcomes.

The helper validates the structure and cryptographic bindings supplied by the release lead. It cannot establish that an external artifact exists, its reviewer approved it, a baseline is complete, or a source check was allowed. Those artifacts must be independently hash-verified before passing an admission. Offline tests use explicitly synthetic admission hashes to exercise this contract; those hashes are not real approvals. No genuine admission file is included in this change. Remedy's possible suite-B alias and all candidates' historical novelty still need baseline reconciliation.

Descriptors reuse stable candidate `runtimeId`, chain, merchant, store, product and variant IDs without renaming collector signals. Defaults are 1,800-second cadence, one-hour source expiry, fail-closed-on-error, no immediate retry, 86,400-second denial pause and 14,400-second rate-limit pause. `bootstrapCandidates: 0` records the required contract; the existing scheduler must enforce bootstrap suppression. The unchanged generic collector retains its bounded single attempt, two requests per product, exact pickup/address/size/identity proof, and configured resource ceilings. New approved merchant configurations use the same collector; no retailer code branch is needed.

`partitionBindings` records exact store/product/variant tuples. `shopifyCohortScopeMatches` checks state, chain, the exact tuple, and any present runtime/poll source ID. Canonical eligibility is separate from ownership: an invalid old canonical mapping must still be owned so it can be vetoed. Existing `storeIds`/`productIds`/`variantIds` lists are also supplied for one-tuple compatibility; do not use their Cartesian combination for future multi-product sources.

The smallest safe implementation is one generic dispatch branch plus narrow admission-aware shared policy changes. The tradeoff is explicit centralized policy work: collection compatibility alone cannot authorize customer inventory or alerts, and negative episode history remains a real persistence requirement.
